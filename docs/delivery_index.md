# 발송 이력 — 발송일 기준 코드 버전과 추출 숫자

병원에 **실제로 보낸** 배포만 기록한다. 발송 3건: 2026-06-24, 2026-08-31, 2026-09-12
(사용자 확인, 2026-09-14). 준비만 하고 보내지 않은 export는 이 문서에 넣지 않는다 —
`output/circe_be/`에 파일이 있다는 것은 발송의 증거가 아니다.

코드 버전은 **발송일 기준**으로 적는다. 런 디렉터리 라벨이나 store mtime이 아니라,
그 산출물이 병원으로 나간 시각의 artemis HEAD다.

| 2026-06-24 | 산출물 위치 미확인 | **없음** | **없음** |
| 2026-08-31 | `output/circe_be/2026-08-31/` + `tte_circe_6studies_arms_20260831.zip`, 6개 시험 12파일 | `745ea83` (08-27 01:33) | **불명 — 08-13 이전** |

세 칸의 "없음 / 불명"은 추정을 포기한 것이 아니라 측정된 사실이다.

- **2026-06-24 — 버전 관리 이전이다.** artemis 최초 커밋은 `6ffd07c` (2026-07-22)로,
  06-24 시점에는 리포지터리가 존재하지 않았다. 이 발송의 코드 버전은 커밋으로 지정할
  수 없고, 산출물도 `output/circe_be/` 아래에 없다(최초 디렉터리는 `2026-08-03`).
- **2026-08-31 — HEAD와 내용의 코드 버전이 다르다.** 발송 시각 HEAD는 `745ea83`이지만,
  이 export는 컨테이너의 live store에서 뽑혔고 그 store는 **08-13에 마지막으로 기록된**
  상태였다. 따라서 산출물이 반영한 코드는 08-13 이전 어느 시점이며 `745ea83`이 아니다.
  (note-018 Row 1, `TTE_STORE_PATH` 결함)
- **2026-09-12 — 유일하게 확정된 건이다.** 반영 커밋 8개가 `PROVENANCE.md`에 기록돼 있다:
  `623e663`, `a2ecba6`, `141ecb7`, `a2fb858`, `c75085c`, `d0ee924`, `c0df6db`, `e8daa37`.
  런 디렉터리는 `output/site_gap/2026-09-15/`이며(라벨이 발송일과 다름), 그 `DELIVERY/`
  6파일과 발송 zip의 md5가 일치함을 확인했다.

`_generationCensus`는 08-31 산출물에 존재하지 않는다(그 회계 필드가 나중에 추가됨).
08-31 행은 `InclusionRules / ConceptSets`만 셀 수 있으므로, 두 행의 총 기준수를 직접
비교하면 안 된다 — 한쪽은 측정값 자체가 없다.

ARISTOTLE·PLATO·LEADER는 08-31에는 포함됐고 09-12에는 빠졌다. 09-12의 기본 배포는
3개 시험이다.

## 이 표가 드러내는 회귀

**CAROLINA는 아주대에서 31/46명이었고, 09-12 발송에서 0/0명이 됐다.** 다른 두 시험은
두 발송 모두 0이므로 변화가 없다. 09-12 발송에서 새로 나빠진 것은 CAROLINA 하나다.

두 발송의 CAROLINA 정의에서 presence를 요구하는 `ALL` 규칙을 직접 비교하면:

| 규칙 | 2026-08-31 (31/46명) | 2026-09-12 (0/0명) |
| --- | --- | --- |
| Body Mass Index | `<= 45`, **단위 조건 없음** | `<= 45`, **`Unit = 9531 (kg/m2)` 요구** |
| HbA1c | `>= 6.5`, `> 7.5`, **단위 조건 없음** | `6.5~8.5`, `> 7.5`, **`Unit = 8554 (%)` 요구** |

두 규칙 모두 `ALL`이므로 AND로 묶이고, 하나만 0을 반환해도 코호트 전체가 0이 된다.
entry event는 두 발송 모두 `DrugEra`(linagliptin / glimepiride)로 동일했고 08-31에
31/46명을 냈으므로, **아주대의 `drug_era`는 비어 있지 않다** — 추정이 아니라 08-31
실측이 배제해 주는 가설이다. 남는 원인은 단위 요구다.

단위 요구를 넣은 커밋은 `141ecb7`("carry the UCUM units the table lacked")과
`956d8e8`("a threshold whose unit was dropped is refused")이고, 같은 방향의 lint가
`5d4dc1d`·`606c686`으로 추가됐다.

같은 함정이 이미 기록돼 있다: note-021은 아주대·동아대·계명대 delivery CDM의 eGFR
13,845행 전부가 **은퇴한 `9117`**을 쓰고 현행 `720870`을 쓰지 않는다고 적었고,
`_UNIT_DEPRECATED_FORMS`로 eGFR만 복구했다(아주대 0 → 112행). BMI의 `9531`과
HbA1c의 `8554`에 같은 처리가 들어갔는지는 이 문서에서 확인하지 않았다.

## 게이트가 이걸 잡지 못한 이유

배포 게이트는 **단위가 없는** bound를 결함으로 잡는다(`unitless value bound`).
**단위가 있고 사이트가 그 concept을 쓰지 않는** 경우는 검사 항목에 없다. 게이트
관점에서 09-12 정의는 08-31 정의보다 개선된 것이고, 병원 실행에서는 31/46명이 0명이
됐다. 게이트가 한 방향으로만 조여져 있다.

## 확정하지 못한 것

- 아주대에서 BMI와 HbA1c의 `unit_concept_id`가 실제로 무엇인지 관측한 적이 없다. 위
  결론은 "단위 요구가 추가됐다"는 정의 쪽 사실과 "31/46 → 0"이라는 실측의 결합이며,
  어느 단위 값 때문에 0이 됐는지는 미확인이다.
- 아주대는 규칙별 attrition을 제공한 적이 없다(People/Records 헤드라인만). 어느 규칙이
  0을 만들었는지 확정하려면 Atlas의 inclusion rule statistics가 필요하다. 판별 쿼리는
  `docs/site_zero_diagnosis_queries.sql`의 Q3(HbA1c 단위 분포)·Q5(BMI 단위 분포).
- 2026-06-24 발송의 산출물 위치와 스터디별 수치는 찾지 못했다.
