**최종 갱신**: 2026-07-28
**상태**: 엔진 구현 완료 · 시뮬레이션 검증 완료 · **3개 병원 데이터 수령·정규화 완료** · 실제 코호트 적응 실행 대기
**관련**: ADR-030(적응 계층), ADR-029(feasibility), ADR-028(대조군), ACHILLES_데이터_요청서.md

---

## 1. 한 줄 요약

병원 CDM에 접근하지 않고도 코호트를 사이트별로 적응시키는 엔진을 만들었고, 가짜 병원 3곳으로 검증을 마쳤다. **2026-07-28 아주대·동아대·계명대 실제 ACHILLES 데이터를 수령해 표준 스냅샷으로 정규화했다**(`data/site_snapshots/`). 남은 것은 실제 TTE 코호트를 이 스냅샷에 컴파일해 적응 리포트를 내는 일이다.

---

## 2. 왜 이걸 만들었나 (배경)

AI 생성 TTE 코호트를 아주대·계명대 CDM에 적용하자 대부분 환자 0명이 나왔다. 결함 A/B/C/D를 개별 수정했지만, 근본 원인은 하나였다.

> 하나의 코호트 정의를 모든 병원에 그대로 배포할 수 없다. 병원마다 vocabulary 매핑·코딩 세분도·도메인 배치·데이터 밀도가 다르다.

그런데 우리는 병원 CDM에 접근할 수 없다. 우리 Synthea에서 측정하는 것은 "틀린 CDM"을 세는 것이고, 병원에 우리 코드를 설치하는 것은 거버넌스 마찰이 크다.

**해법**: 병원에서 **ACHILLES 집계 파일 한 장**(개념별 환자 수)만 받고, 적응은 우리 쪽에서 수행한다.

## 4. 수령 데이터 현황 (2026-07-28)

아주대·동아대·계명대 3곳에서 ACHILLES export를 받아 표준 스냅샷으로 정규화했다.
상세 기록: **[수령데이터_정규화.md](./수령데이터_정규화.md)**

| 스냅샷 | 총 행수 | 비고 |
|--------|---------|------|
| `data/site_snapshots/ajou.zip` | 18,695 | xlsx(domain,concept_id,count) 원본 |
| `data/site_snapshots/donga.zip` | 16,992 | 도메인별 CSV(영문 헤더) |
| `data/site_snapshots/keimyung.zip` | 10,319 | 번호 CSV(한글 헤더), 도메인은 내용으로 판별 |

세 스냅샷 모두 `load_achilles_snapshot()` 통과, 값 무결성 원본 대조 일치.

**데이터에서 확인된 핵심 사실**
- 세 병원 모두 약물을 **제품(RxNorm Extension) 수준**으로 코딩 — 성분 개념(sitagliptin·metformin 등)은 **전부 부재**. 성분 ID로 정의된 코호트는 구조적으로 0명이 된다 → descendant 확장 필수
- 고혈압이 상위 개념(316866)이 아니라 하위 개념(320128)으로 코딩 → granularity 적응 필요
- `Dietary regimen`은 세 병원 모두 **존재**(Synthea는 0) — feasibility를 사이트에서 측정해야 하는 이유가 실측으로 확인됨

**미확정 (해석에 영향)**
- `smallCellCount`를 잠정 **0**으로 설정했다. 실제 억제가 적용된 사이트라면 "행 없음"을 0명으로 오판하게 되므로, 각 사이트의 실제 값을 확인해 스냅샷을 재생성해야 한다.
- 아주대 `device` 도메인 738행은 우리 6-analysis 계약 밖이라 드롭했다(현행 유지).

## 5. 적응 실행 절차

### 5-1. 스냅샷 준비
이미 정규화된 스냅샷이 `data/site_snapshots/`에 있다. 새 데이터를 받았거나 `smallCellCount`가 확정되면 다시 생성한다(스냅샷은 gitignore 대상이라 재생성으로 복원한다).

```bash
python3 scripts/normalize_site_achilles.py \
  --input /home/bilab/work/projects/Broadsea/achilles_data \
  --output data/site_snapshots \
  --run-date <ACHILLES 실행일> --small-cell-count <확인된 값>
```

### 5-2. 적응 실행

```bash
cd artemis
.venv/bin/python scripts/adapt_site_cdm.py \
  --snapshot data/site_snapshots/<site>.zip \
  --circe <대상 코호트>.json \
  --vocabulary-map tests/fixtures/site_adaptation/vocabulary_map.json \
  --comparator-artifact <대조군 후보>.json \
  --output site_report.json
```

> `--vocabulary-map`은 현재 fixture용 축약본이다. 실 사용 시 해당 사이트의 vocabulary 버전에 맞는 concept_ancestor 매핑으로 교체해야 한다(미해결 항목, 6절 참조).

### 5-3. 리포트 읽는 법

| 필드 | 의미 |
|------|------|
| `status: "proposed"` | 자동 적용 안 함 — 사람이 승인해야 반영 |
| `criteriaEvidence[]` | 기준별 role(entry/inclusion/exclusion) · state · 환자 수 |
| `proposedChanges[]` | `VERIFY_THEN_DROP`(0 후보 — 2차 확인 후 제외) / `USE_POPULATED_DESCENDANTS`(하위형으로 재해석) |
| `verificationRequests[]` | ACHILLES로 판정 불가 — 사이트가 직접 쿼리해야 할 항목(시간창·값/단위) |
| `comparatorGrounding[]` | 대조약 후보별 populated / site_query_required / absent |
| `inputSignature` | 입력 해시 — 재현·캐시 키 |

### 5-4. 검토 후 반영
`proposedChanges`를 담당자가 검토·승인 → Circe 사본에 적용 → WebAPI로 코호트 생성 → 환자 수 확인.
