#### 1. `No pregnant` — **입력 source에 아예 없음**

```

TROY에는 "No pregnant" rule이 있지만, LEADER trial의 공개 문서(NCT + papers)에는 pregnancy exclusion이 명시적으로 기술되지 않음. **구조적 한계** — 자동화로 해결 불가.

#### 2. `No acute decompensation` — **Rule은 있지만 concept 불일치**

```
Agent 1:  ✅ "Acute decompensation of glycemic control" rule 생성
Agent 2:  ✅ 12 raw → 180 resolved concepts 매핑
TROY:     443727 (Diabetic ketoacidosis) + 8 descendants

TROY 큐레이터는 **임상적 판단**으로 "decompensation" → DKA로 해석. Agent 2는 텍스트 검색으로 전혀 다른 concept을 찾음. → **RFC-008 UMLS CUI Bridging**으로 해결 필요.

### 💡 Agent 1 역할 축소 결정 (ADR-017)

**배경**: Agent 1이 현재 (1) NCT fetch + PubMed 검색 + PDF enrichment와 (2) LLM IR 생성을 모두 담당. 그런데 (1)은 결정적이고 (2)만 비결정적 → 관심사가 혼합되어 있음.

| | AS-IS | TO-BE |
|---|---|---|
| **입력** | NCT 번호 | 정리된 TrialData (criteria 리스트) |
| **Data fetch** | Agent 1 내부 (NCT + PubMed + PDF) | **분리** → Data Layer |
| **IR 구성** | Agent 1 LLM | Agent 1 LLM (캐시 적용) |
| **핵심 역할** | 전체 | **sub-criteria 분해**만 |

**결정 근거**:
1. Data fetching(pdftotext + regex)은 이미 결정적 — Agent의 역할이 아님
2. Agent 1의 진짜 가치는 **LLM 기반 sub-criteria 분해** (e.g., "prior CV disease" → MI, Stroke, Revascularization 등)
3. 분리하면 TrialData를 다른 경로(직접 입력, 다른 DB)에서도 받을 수 있어 재사용성 증가
4. Agent 1을 TrialData 입력으로 단위 테스트 가능 (PDF/네트워크 의존 제거)

**영향**: 현재는 IR 캐시로 즉시 해결. 리팩터링(fetch 로직 → data layer 이동)은 후속 작업.

## KG Expander 3가지 확장 전략 비교 (00:05)

`kg_expander.py`에 기존 2개 + 신규 1개 = 3가지 "위로 올라가는" 메서드 존재:

### 1. `get_ancestors()` — 그냥 위로 보기만 (기존)
```
seed → 상위 ancestor 목록 반환 (descendant_count 포함)
```
- **역할**: Critic에게 "이 ancestor 중에서 골라라" 제시용 후보 목록
- **확장 없음**: ancestor 자체만 반환, descendants 미확장
- **용도**: `clinical` 전략에서 anchor 역할. Critic이 context를 이해하도록 상위 개념 제공
- **예**: Cerebral infarction → [Ischemic encephalopathy, Disorder of brain] 반환 (이 ancestor들만, 그 아래 concepts는 안 줌)

### 2. `expand_from_ancestors()` — leaf node 보완용 2-hop (기존)
```
seed(leaf) → 1단계 parent → 그 parent의 descendants 확장
```
- **역할**: seed가 **leaf node** (descendants=0)일 때만 작동하는 보완 로직
- **제한**: 1단계 parent만 올라감 (max 1-hop up)
- **IC 필터 없음**: parent의 일반성을 검증하지 않음
- **예**: "Completed stroke" (leaf) → parent "CVA" → CVA의 하위 concepts 가져옴

### 3. `ancestor_climb()` — IC 기반 계층 등반 (🆕 신규)
```
seed → IC 기준으로 적절한 ancestor 선택 → 그 ancestor의 모든 descendants 확장
```
- **역할**: **모든 seed** (leaf든 아니든)에서 의미적으로 적절한 상위 개념까지 올라간 뒤 descendants 전부 확장
- **핵심 차이**: IC threshold로 "어디까지 올라갈지" 결정 (IC > 8.0)
- **필터링 (Cypher 레벨)**: `concept_class_id != 'Clinical Finding'` + domain 필터
- **필터링 (Python 레벨)**: IC > 8.0 (= desc < ~10,700)
- **예**: "Cerebral infarction" (IC=15.14) → ancestor "Disorder of brain" (IC=9.51, ✅) → 3,774 descendants 확장. "Disease" (IC=4.91, ❌) 거부.

### 비교표

| | `get_ancestors` | `expand_from_ancestors` | `ancestor_climb` 🆕 |
|---|---|---|---|
| **방향** | 위로 보기만 | 위 1단계 → 아래로 | 위 N단계 → 아래로 |
| **작동 조건** | 항상 | leaf node일 때만 | 항상 |
| **ancestor 선택** | 전부 반환 | 1-hop parent (무조건) | **IC > 8.0 통과한 best** |
| **descendants 확장** | ❌ 안 함 | ✅ parent의 하위만 | ✅ best ancestor의 전체 하위 |
| **IC 필터** | ❌ | ❌ | ✅ |
| **domain 필터** | ❌ | ✅ | ✅ (Cypher 레벨) |
| **class 필터** | ❌ | ❌ | ✅ `!= Clinical Finding` |
| **LLM 의존** | 없음 | 없음 | 없음 |
| **효과** | Critic 참고용 | leaf 보완 | **체계적 hierarchy 확장** |

### 버그 2: 잘못된 ancestor 선택 — Neo4j partial desc_count (🔴 Critical)
- Neo4j에 `min_levels_of_separation BETWEEN 1 AND 3`으로만 로딩 → **desc_count 부정확**
- "Traumatic or non-traumatic injury"가 Neo4j에서 desc=수백 (3-hop내만) → IC>8 통과 → 잘못 선택
